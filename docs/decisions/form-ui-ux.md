# UI/UX: формы задач и заявок (дизайн-система форм)

Документ фиксирует визуальные правила, по которым живут страницы форм
`#dob_tasks/<id>?list=<GUID>` — **заявка ДОБ** и **задача типа контента**
(«Результат проверки ООБ»). Обе формы обязаны выглядеть одинаково: один и тот же
порядок блоков, одни отступы, одна типографика. Источник правды по стилям —
`src/features/dob/lib/formStyles.js` (экспорты `FORM_*`, `RESULT_TOGGLE_GROUP_SX`).

## 1. Порядок содержимого страницы (сверху вниз)

1. **Шапка (sticky AppBar, 48 px).** Меню, «назад», затем
   **«Задача #<Id> · <Название задачи>»** — номер и название рядом, название
   обрезается многоточием (не ломает строку). Справа: «обновление…» (если идёт
   фоновое обновление), «Обновить», основная кнопка **«Сохранить»**.
2. **Описание задачи** (`FORM_TASK_HEAD_SX`): метка `ОПИСАНИЕ ЗАДАЧИ` + текст
   (rich-теги снимаются, абзацы сохраняются как переводы строк).
3. **Результат проверки** (только задача типа контента): группа кнопок
   результирующего выбора (`role="group"`), выбранная кнопка залита фирменным
   синим `#171c8f`.
4. **Основное поле формы** — «Описание результата проверки» (rich-текст CKEditor)
   отдельной секцией: это главное поле, оно не «прячется» среди прочих.
5. **«Остальные поля»** — секция с сеткой 1 / 3 / 4 колонки: тип ошибки,
   количество ошибок, виновные и т. п.
6. **Действия** (`FORM_ACTIONS_SX`): «Отмена» (контур) и «Сохранить» (градиент).
7. Предупреждение о незаполненных обязательных полях — над кнопками, а не в шапке.

Почему так: пользователь сначала понимает **что за задача** (номер, название,
описание), затем отвечает на **главный вопрос** (результат), затем описывает
результат, и только потом заполняет сопутствующие поля. «Остальные поля» не могут
быть первым блоком страницы.

## 2. Поля и выравнивание подписей

* Однострочные поля — `min-height: 40px` (штатная высота MUI `size="small"`),
  `border-radius: 4px`; подпись (`label`) и значение — `font-size: 13px`,
  `line-height: 1.35`. Одинаковая метрика у обоих убирает «съехавшую» подпись
  внутри инпута.
* Многострочные (`Note`) и множественные (`MultiChoice`, «Пользователь или
  группа») поля **не получают фиксированную высоту** — растут по содержимому,
  чтобы чипы/строки не обрезались.
* **Пользователь или группа** занимает широкую ячейку (`FORM_FIELD_WIDE_SX`,
  2 колонки): имя и чипы помещаются целиком, ничего не выезжает за края формы.
* Обязательность показывается звёздочкой только там, где SharePoint вернул
  `Required: true` (никаких «догадок» приложения).
* Rich-текст и длинные заметки занимают всю ширину сетки (`FORM_FIELD_FULL_SX`).

## 3. Чипы людей

* Чип содержит **только имя** (`Фамилия Имя Отчество`), без должности/департамента.
* Полные сведения (Должность, Департамент, Офис, Учётная запись) — в **карточке
  по клику** (Popover `person-details`); повторный клик закрывает карточку.
* У чипа — `max-width` и многоточие; при наведении `title` показывает
  «Имя — Должность · Департамент · Офис».
* Крестик удаляет значение и не открывает карточку.

## 4. Кнопки, состояния, цвета

| Элемент | Оформление |
| --- | --- |
| Основная кнопка | градиент `#171c8f → #10146a`, белый текст, высота 32 px |
| Вторичная кнопка | контур, тот же радиус/высота |
| Кнопки результата | `ToggleButtonGroup`, выбранная — залита `#171c8f`, высота 36 px |
| Секция | белая карточка, рамка `rgba(23,28,143,.14)`, паддинг 8–10 px |
| Заголовок секции | акцентная полоса 4×18 px + текст `font-weight: 800`, цвет `#171c8f` |
| Описание задачи | подложка `#f8f9ff` с рамкой |
| Ошибка/обязательное поле | `#c62828`, подпись под полем |

Состояния кнопок: `hover` — светлее/темнее на 6–8 %, `disabled` — без градиента
и с серым текстом, `loading` — `CircularProgress` вместо иконки и текст
«Сохранение…». Действия блокируются на время отправки (двойная отправка
невозможна).

## 5. Доступность и адаптивность

* Иконочные кнопки имеют `aria-label` («Открыть меню», «К задачам»).
* Группа кнопок результата — настоящая `role="group"`; выбранное состояние
  передаётся `aria-pressed` (MUI ToggleButton).
* Сетка полей адаптивная: 1 колонка на телефоне, 3 на планшете/десктопе,
  4 на широком экране; `minmax(0, 1fr)` + `min-width: 0` не дают содержимому
  выпирать и вызывать горизонтальный скролл (`overflow-x: hidden` у страницы).
* Контраст текста: основной — `#171c8f`/`text.primary`, второстепенный —
  `text.secondary`, ошибки — `#c62828` (≥ 4.5:1 на белом).

## 9. Доступность действий в таблице и отклик UI (2026-10-04)

**Правила доступности действий** (`src/features/tasks/lib/rowActions.js`, един для
табличного попапа и legacy-набора `TasksGrid`):

| Состояние задачи | Что видно в меню строки |
|---|---|
| **не взята в работу** (любой источник, «Не начата» и прочие незавершённые) | только **«Взять в работу»** |
| main, «В работе» у меня | кнопки результата + **«Изменить»** |
| ДОБ, «В работе» у меня | **«Изменить»** (форма ДОБ) |
| «В работе» у другого | плашка «В работе у X» и ничего больше |
| **любая завершённая** | **ни одной кнопки** — только плашка «Задача завершена» |

Ключевое правило (единое для main и ДОБ): **«Изменить» доступна только после
взятия в работу** — иначе форму задачи можно открыть в обход «Взять в работу».
Завершённые задачи не дают ни «Взять в работу», ни «Изменить», ни кнопок
результата — ни в таблице, ни в карточке (`ExternalTaskCard`, `TaskCard`).

**Визуальный отклик «задача обновляется»** (`TasksGrid`):

* **кружок-лоадер ВНУТРИ ячейки `Id`** той строки, по которой идёт действие
  (`IdCell`, `data-testid="tasks-row-spinner"`): номер задачи остаётся на месте,
  ничего не сдвигается;
* строка дополнительно помечается классами `tasks-row-busy tasks-row-updating` /
  `tasks-row-taking` — лёгкая подсветка фона (CSS в `src/index.css`).

Почему именно так: AG Grid позиционирует строки **абсолютно**, поэтому любые
вставки над строкой (плашка/полоса прогресса) и тем более свой `position` у
`.ag-row` ломают раскладку — строка «уезжает», под ней появляется пропуск.
Лоадер внутри ячейки — единственный вариант, который ничего не двигает. Занятая
задача передаётся в грид через `context` (объект мемоизирован), а при её смене
обновляется только колонка `Id` (`refreshCells`) плюс `redrawRows` для подсветки.

**Скорость поповера.** Тормоза при клике по строке лечатся тремя вещами:

1. таблица AG Grid вынесена в `memo`-компонент `GridTable` — открытие/закрытие/
   скролл попапа больше не перерисовывает грид (в тесте проверяется, что DOM-узел
   ячейки остаётся тем же);
2. набор действий строки собирается один раз на открытие меню
   (`useMemo(..., [menuRow, actionsForRow])`), а не на каждый рендер;
3. выделение строки — через `React.startTransition` (низкий приоритет): попап
   открывается, не дожидаясь пересчёта подсказки под таблицей; анимация попапа
   укорочена до 110/80 мс (входа/выхода) вместо стандартных 225/195.

Тесты: `TasksGrid.perf.test.jsx` (счётчик рендеров грида: 0 рендеров на
открытие/переезд/закрытие поповера; без `memo` — лишний рендер, тест падает),
`TasksGrid.rowActions.test.jsx` (кружок в ячейке Id нужной строки и его
исчезновение после записи), `rowActions.test.js` (таблица правил доступности).

## 10. Завершение задачи в режиме `#tasks/<ID>` (2026-10-04)

Карточка в hash-режиме живёт в отдельном state `elementTaskMatch`
(`useHashElement`) и **не** обновляется из списка задач. Поэтому `completeTask`
обязан патчить её явно — иначе после выполнения действия задача остаётся
«в работе» до следующего опроса (`useHashPolling`, до 60 с).

* Оптимистичный патч (`_optimistic`) по-прежнему **не** трогает
  `Status`/`PercentComplete`: иначе карточка исчезала бы (задача уезжает из
  вкладки «В работе») до ответа сервера и оверлей «Сохранение...» не был виден.
* После **подтверждённой** записи (все ветки: прямой MERGE, фолбэки Edm.Boolean/
  Edm.String/AdditionalActions, «уже закрыта другим пользователем») в
  `elementTaskMatch` уходит `Status: <Завершена>`, `PercentComplete: 1`,
  результат и `EditorTitle` — карточка сразу показывает «Задача выполнена».

Тесты: `hooks/__tests__/useTaskMutations.test.js` (патч закрытия; оптимистичный
патч статус не трогает; «уже закрыта на сервере»), `components/__tests__/
TasksHashContent.completed.test.jsx` (карточка переключается в завершённое
состояние).

### 10.1 Первый переход по `#tasks/<ID>`: лоадер, а не «не найдено»

Первый переход открывает задачу, которой ещё нет в загруженном списке:
`resolveHashTarget` догружает её с сервера (`fetchFullTask`). Пока идёт запрос,
`elementTaskMatch` пуст, а флаги `elementLoading`/`elementTaskSearching` ещё не
выставлены (effect пассивный — он выполняется ПОСЛЕ первого кадра). Раньше в
этом окне компонент рисовал плашку «Элемент #… не найден» и только затем —
карточку: пользователь видел ложное «не найдено».

Правило теперь явное: **поиск завершён**, только когда есть задача
(`elementTaskMatch`) либо явный результат — `elementNotFound` или `elementError`.
Пока ничего из этого нет — показывается лоадер (`data-testid="hash-loading"`).
Плашка «не найдено» рисуется лишь по факту завершённого поиска без результата.

### 10.2 Форма задачи: сначала «Взять в работу», потом данные (2026-10-09)

Задачу ДОБ/основного списка можно открыть прямой ссылкой
`#dob_tasks/<id>?list=<GUID>` — в обход таблицы, где кнопка «Взять в работу»
обязательна и стоит ещё до «Изменить» (§9). Форма раньше не знала про статус
и позволяла сохранить результат задачи со статусом «Не начата»: данные уходили
на сервер без исполнителя и без смены статуса.

Правило: **пока задача не взята в работу, форма закрыта «шлюзом»**
(`src/features/dob/DobTaskEditView.jsx`, `data-testid="dob-take-gate"`):

* `needsTake = item && isNotStartedStatus(Status) && !completed && !inProgress`
  — требовать взятие только при ЯВНОМ статусе «не начата»; у заявок без поля
  `Status` форма остаётся доступной, как раньше.
* Вместо полей — карточка с пояснением и кнопка «Взять в работу»
  (`PlayArrowIcon`, та же градиентная плашка, что и в таблице); на время запроса
  крутится `CircularProgress` и кнопка заблокирована.
* Кнопка «Сохранить» недоступна, а `validateAndSave`/`handleCheckResultSubmit`
  дополнительно отсекают сохранение (на случай вызова с клавиатуры/из шапки).
* Взятие — `takeDobTaskInWork(id, listGuid, { choices })` в
  `src/features/dob/api/dobApi.js`: сначала читается свежий
  `Status/PercentComplete` (за время чтения формы задача могла измениться),
  завершённую задачу брать нельзя (`reason: 'completed'`), уже «в работе»
  — форма просто открывается (`reason: 'already-taken'`). Статус «в работе»
  берётся **из choices поля `Status` этого списка** (`pickInProgressChoice`):
  у списков он разный, хардкод «В работе» — только фолбэк.
* После успешного MERGE — `invalidateQueries` и `refetch` элемента, шлюз уходит,
  форма открывается с уже обновлённым статусом (без перезагрузки страницы).

Тесты: `dob/__tests__/dobApi.takeInWork.test.js` (5: MERGE «в работе» из choices,
готовые choices без лишнего запроса, фолбэк, `already-taken`, `completed`) и
`dob/__tests__/DobTaskEditView.takeGate.test.jsx` (3: шлюз вместо формы и
недоступное «Сохранить»; взятие уходит в тот же список и открывает форму;
«В работе» — шлюза нет).

## 7. Картинки и вложения (2026-10-04)

* Каждая картинка, вставленная в rich-текст (ckeditor: вставка из буфера, drag&drop,
  выбор файла), **загружается вложением элемента** — вложений может быть сколько
  угодно. В текст при этом подставляется ССЫЛКА на вложение (в редакторе — рабочий
  адрес `/dob-api/…` в dev, на сохранении — серверный путь `/sites/…`), поэтому
  base64 в SharePoint не попадает; если загрузка не удалась, сохранение блокируется
  с понятным сообщением (см. `rich-images-and-dob-flag.md`).
* Список вложений показан прямо под формой (блок «Вложения (N)», чипы): клик —
  открыть, крестик — удалить. Удаление вложения убирает картинку из текста.
* Если картинку убрали из текста — её вложение удаляется автоматически
  (diff по html, `src/features/dob/lib/richImages.js`).
* Загрузка сопровождается индикатором (LinearProgress + состояние «загружается» в
  редакторе) и уведомлением об успехе/ошибке; ошибка загрузки не теряет текст.
* Модульные тесты: `dob/__tests__/richImages.test.js` (разбор src, имя файла, diff),
  `dob/__tests__/DobTaskEditView.checkTask.test.jsx` (две картинки → два вложения),
  `tasks/__tests__/ContentTypeResultDialog.test.jsx` (обработчик загрузки прокинут).

## 8. Валидация и мелкая геометрия полей (2026-10-04)

* **Строка шаблонов rich-редактора.** Тема приложения поднимает все outlined-поля до
  56 px (`App.jsx`, `MuiOutlinedInput.height`). В строке шаблонов («Шаблон:» и
  «Название нового шаблона») это выглядело «очень высокими инпутами», поэтому панель
  шаблонов ограничивает их 32 px собственным `sx` (`TEMPLATE_TOOLBAR_SX` в
  `RichEditor.jsx`) — вровень с кнопками «Сохранить»/«Удалить».
* **Акцент незаполненного.** Ошибка валидации видна на трёх уровнях: поле
  (`error` + подпись «Обязательное поле»), блок/секция (`FORM_INVALID_SECTION_SX`:
  красная рамка, красная полоса заголовка, `data-dob-invalid`/`data-ct-invalid`) и
  snackbar с перечнем пропусков («Заполните обязательные поля: …»). Плюс прокрутка к
  первому пропуску и фокус в его инпут — в длинной форме «Остальные поля» ошибку
  иначе не видно.
* **Обязательность — только `Required` из SharePoint.** Клиент ничего не досочиняет:
  что помечено обязательным в списке/типе контента, то и требует форма.
* **Вложения — внутри редактора.** Блок «Вложения (N)» живёт в нижней полосе
  `RichEditor` (`data-testid="rich-editor-footer"`): картинки из текста сохраняются
  вложениями и удаляются рядом с текстом. Пустое состояние показывает подсказку
  внутри того же блока.
* **Числовое поле** («Кол-во ошибок») — `FORM_NUMBER_FIELD_SX`: та же высота
  `FIELD_HEIGHT` (40px), что у остальных однострочных полей, спиннеры скрыты.

## 11. Завершённые задачи, счётчик бейджа и «Кому назначено» (2026-10-09)

### 11.1 Завершённую задачу править нельзя — ни в таблице, ни по прямой ссылке

Раньше форма `#dob_tasks/<id>?list=<GUID>` не смотрела на статус: завершённую
задачу можно было открыть и сохранить в неё результат (данные уходили в уже
закрытую задачу). Таблица такое не давала (`rowActions`: завершённой — только
плашка), а прямая ссылка — да. Теперь правило одно для всех интерфейсов:

* `DobTaskEditView`: `readOnly = isCompletedStatus(Status, PercentComplete)` —
  форма открывается **только на просмотр**: плашка «Задача завершена — форма
  открыта только для просмотра» (`data-testid="dob-readonly-banner"`), в шапке
  вместо «Сохранить» — чип «Завершена · только просмотр»;
* все контролы недоступны: поля (`editable = isEditableField(f) && !readOnly`),
  rich-редактор (`readOnly`), кнопки результата, вложения (у чипов нет крестика,
  обработчики загрузки/удаления не передаются);
* `ContentTypeResultDialog` получил проп `readOnly`: контролы заблокированы,
  «Сохранить» заменена на «Закрыть», `handleSubmit` отсекает запись;
* страховки: `validateAndSave` и `handleCheckResultSubmit` выходят без записи.

Тесты: `dob/__tests__/DobTaskEditView.readOnly.test.jsx` (3: плашка/чип и нет
«Сохранить»; кнопки результата недоступны и записи не уходит; контроль —
незавершённая задача редактируется).

### 11.2 Счётчик активных задач в бургер-меню: один источник правды

Бейдж «слетал» при переключении интерфейсов: в одно состояние писали двое —
опросчик `App` (фильтр «я + группы рассылки») и `TasksView` через
`onCountChange` (число по **загруженной, отфильтрованной** выборке; ушёл из
интерфейса задач — писать перестал), а ответы приходили вразнобой.

Теперь счёт считает только `features/tasks/hooks/useActiveTasksCount.js`:

* фильтр «я + мои группы» (`AssignedToId eq … or …`), фолбэк `AssignedTo/Id`;
* **последний запущенный запрос побеждает** (иначе ответ «личного» фильтра,
  пришедший позже, затирал свежий счёт с группами);
* одинаковый фильтр не шлёт второй запрос, пока первый в полёте;
* ошибка сети НЕ обнуляет счётчик (бейдж не пропадает из-за сети);
* интервал 60 с + фокус/видимость окна;
* `TasksView` больше не передаёт число, а зовёт `onTasksChanged` — «данные
  изменились, пересчитай».

Тесты: `features/tasks/hooks/__tests__/useActiveTasksCount.test.js` (7: счёт по
фильтру; поздний ответ не затирает свежий; ошибка сети не обнуляет; дедуп

### 11.3 «Кому назначено» — кнопка с иконкой человека или группы

Раньше `AssignedTo` показывали просто строкой. Теперь во всех интерфейсах это
кнопка `AssignedToButtons` (`features/tasks/components/AssignedToButtons.jsx`):

* `startIcon`: **человек** (`PersonIcon`) или **группа** (`GroupsIcon`) — тип
  уточняется лениво по `AssignedToId` в `lib/assignees.js` (`resolvePrincipal`);
  кэш в sessionStorage + дедуп «в полёте». У задачи внешнего сайта (ДОБ) Id
  уточняется на ЕЁ сайте — иначе тот же Id указал бы на другого человека.
  **Как определяется тип.** `/web/getuserbyid(<id>)` в SharePoint возвращает
  НЕ только людей — группы тоже лежат в User Information List, поэтому
  «нашлась запись ⇒ это человек» — ошибка (у групп стояла иконка человека).
  Тип даёт `PrincipalType` (`SP.PrincipalType`, битовая маска):
  `1` — пользователь, `2` — список рассылки, `4` — security-группа,
  `8` — группа SharePoint; всё, что `2|4|8` — **группа**. Если `PrincipalType`
  не приехал — уточняем `/web/sitegroups/getbyid(<id>)` (оттуда отдаются только
  группы). Ни там ни там — тип неизвестен, показываем иконку человека;
* многозначная колонка — кнопка на каждого исполнителя;
* клик открывает карточку принципала: тип, имя, учётная запись, почта, Id;
* клик по кнопке не открывает ни саму задачу, ни поповер действий строки.
  Стоп делается **в фазе погружения** (`onClickCapture` + `stopPropagation`):
  AG Grid слушает клик на своём контейнере `.ag-root-wrapper`, а React
  навешивает обработчики на корень — обычный `stopPropagation` в `onClick`
  сработал бы уже ПОСЛЕ того, как грид открыл поповер. Плюс страховка в
  `TasksGrid.onCellClicked/onRowDoubleClicked`: клик из
  `[data-testid="assigned-to-button"]` игнорируется.
  Оба слоя проверены по отдельности (убирали один — поповер не открывался);
  Аналогичная ошибка исправлена в `src/tasks/principalDetails.js` — оттуда тип
  принципала (`kindHint`) попадает в `distribution.classifyPrincipal`;
* вид кнопки: серая (`#6b7280`), кегль `0.72rem`, высота 22 px — под подписи
  карточки, а не под кнопки действий; при наведении — фирменный синий.

Подключено: таблица `TasksGrid` (колонка «Кому назначено» через
`AssignedToCell` + шапка попапа строки), `TaskCard`, `ExternalTaskCard`,
`TaskElementDialog`.

Тесты: `features/tasks/__tests__/AssignedToButtons.test.jsx` (8: пользователь с
почтой, группа, пусто, несколько исполнителей, разбор `parseAssignees`).

### 11.4 Завершённую задачу нельзя править и прямо в таблице ДОБ (2026-10-09)

Список ДОБ (`#dob_tasks`, `DobGrid`) — это **editable-грид**: двойной клик по
ячейке меняет значение, правки копятся в `dirty` и уезжают пакетным MERGE по
кнопке «Сохранить». Ограничения «завершённую не править» там не было — строку
со статусом «Завершена» можно было менять ячейкой.

Теперь правило одно для всех интерфейсов и для таблицы тоже:

* `lib/dobRowStatus.js` — `statusInternalOf(fields)` (колонка «Статус» может
  называться `OData__…`) и `isRowCompleted(row, statusInternal)`
  (`isCompletedStatus` по `Status`/`PercentComplete`);
* в `DobGrid` `editable` у колонки — **функция**: ячейка недоступна, если строка
  завершена (а также для Calculated, как раньше);
* `onCellValueChanged` не копит правку по завершённой строке — «Сохранить» не
  запишет её пакетом;
* строка помечается классом `dob-row-completed` (`rowClassRules`), в
  `src/index.css` — только `background-color` (`.ag-row` позиционируется AG Grid
  абсолютно, см. §9).

Тесты: `dob/__tests__/dobRowStatus.test.js` (9) и

## 12. Пять правок интерфейса (2026-10-10)

### 12.1 Нижняя строка карточки без «лесенки»

`Исполнитель: <кнопка> • Статус: …` — подписи и кнопка «Кому назначено» стояли
ВНУТРИ одного текстового узла. Кнопка — inline-flex с иконкой, а такой элемент
выравнивается по baseline своей иконки (у `<svg>` baseline = нижний край), плюс
`min-height` 22 px раздвигал строку: подписи оказывались на разных высотах.

* подписи и кнопка стали элементами одной flex-строки
  (`CARD_FOOTER_ROW_SX`: `display: inline-flex`, `align-items: center`) —
  в `TaskCard` (7 мест), `ExternalTaskCard`, `TaskElementDialog`;
* сама кнопка: `vertical-align: middle`, `line-height: inherit` и `height: auto`
  (высота берётся от строки подписи, а не числом), `min-height: 0` — иначе
  встроенный `min-height` MUI (30 px у `size="small"`) раздвигал строку;
* пробелы между подписями заданы текстом (`"Исполнитель: "`, `" • Статус: "`) —
  иначе flex их схлопнул бы и `textContent` карточки изменился.

Тест: `tasks/__tests__/TaskCardFooterAlign.test.jsx` (4).

### 12.2 «Виновные» в выполненной заявке ДОБ

Симптом: в `#dob_tasks/906?list=…` поле «Виновные» (`Guilty`, многозначное
«Пользователь или группа») пустое, хотя в списке заполнено.

Причина (главная): в SharePoint многократная колонка людей отдаётся как
`TypeAsString = "UserMulti"`, а одиночная — как `"User"`. Фильтр колонок для
`$expand` проверял **только** `'user'`, поэтому «Виновные» в `$expand` вообще не
попали и SharePoint их не возвращал: запрос уходил как
`$expand=Author,Editor,AttachmentFiles,UserFail` — без `Guilty`.

Вторая причина: SharePoint не всегда раскрывает многозначное User-поле даже с
`expand` (колонка скрыта, слишком много expands, старая ферма) — тогда в ответе
есть только `GuiltyId`, а `Guilty` пуст. Раньше форма читала только `Guilty`.

* общий признак «поле людей» — `isUserFieldType` / `isUserField`
  (`dob/lib/dobFormFields.js`): и `User`, и `UserMulti`. Он же используется в
  `dobApi` (`$expand`), в `DobGrid` (колонка людей), в форме и в отображении
  значений;

* `DobTaskEditView`: людей дочитываем по Id с того же сайта — `getuserbyid` →
  `sitegroups/getbyid` (переиспользует `tasks/lib/assignees.resolvePrincipal`,
  поэтому тип человек/группа берётся из `PrincipalType`); кэш в памяти сессии.
  Дочитка нужна в ДВУХ случаях, и оба дают пустые чипы:
  * поле не раскрыто вообще — в ответе только `<Internal>Id`;
  * поле раскрыто, но **без имён** (`Guilty: { results: [{ Id: 12 }] }`) — так
    бывает, когда `$expand` сработал, а в `$select` не было `<Поле>/Title`.
  Уже заполненные имена не перетираются, форма значения сохраняется
  (массив / `results` / одиночный объект);
* `dobApi.getDobItem` получил те же ретраи, что и списочный запрос: если
  SharePoint отвечает 400 на `$expand` конкретной колонки, проблемное поле
  убирается и запрос повторяется (до 5 попыток). Без этого элемент не открывался
  вообще, либо часть полей приходила пустой.

Тесты: `dob/__tests__/DobTaskEditView.guiltyById.test.jsx` (9 — оба случая,
частичное заполнение, одиночное поле, `UserMulti`, кэш) и
`dob/__tests__/dobApi.userMultiExpand.test.js` (3 — `UserMulti` попадает в
`$expand` и `$select`).

### 12.3 Переключатель «Карточки / Таблица» — только на десктопе

`ViewModeToggle` скрыт на xs/sm (`display: { xs: "none", md: "inline-flex" }`):
на узком экране таблица нечитаема (горизонтальный скролл + popup действий, не
помещающийся в экран), поэтому там остаются только карточки. Скрытие сделано
CSS-брейкпоинтом, а не JS-замером ширины, — чтобы не мигало при первой
отрисовке.

Выбор режима запоминается (`useViewMode`), поэтому скрытие переключателя
само по себе ловушка: зайдя с телефона после десктопа, пользователь остался бы
в таблице без возможности вернуться. В `TasksView` добавлено принудительное
`const viewMode = narrowScreen ? "cards" : viewModeView` (md-down через
`useMediaQuery`) — оно же управляет и режимом загрузки данных
(`useTasksTableData({ mode })`).

Тесты: `tasks/__tests__/ViewModeToggle.test.jsx` (4) и
`tasks/__tests__/TasksView.completedTable.test.jsx` (4, включая «на узком экране
таблицы нет»).

## 13. Таблица задач: имя исполнителя, фильтр «Я исполнитель», заливка строк и «Срок» (2026-10-10)

### 13.1 «Кому назначено» без имени — показываем ФИО, а не «Id 10»

Симптом: в карточке `#tasks/25214` нижняя строка читалась как
`Исполнитель: Id 10 • Статус: Не начата`.

Причина: задача приходит не всегда с именем принципала. `$expand=AssignedTo`
срабатывает не у всех источников, а hash-путь может отдать CAML-кандидата вообще
без `expand` (когда `fetchFullTask` вернул 401/403) — тогда в задаче есть только
`AssignedToId`, и `AssignedToButtons` рисовала запасной вариант `Id <номер>`.

* `AssignedToButtons` уже ходила за типом принципала (`resolveAssigneeCached` →
  `getuserbyid` / `sitegroups/getbyid`, кэш + дедуп «в полёте»), но сохраняла
  только `kind`. Теперь держим `{ kind, title }` и берём имя оттуда, если в самой
  задаче его нет. Запросов больше не стало — тот же самый, что и раньше;
* `Id <номер>` остался последним вариантом: нет ни имени в задаче, ни доступа к
  SharePoint;
* в диалог принципала имя передаётся уже уточнённым, чтобы «Имя» не пустело на
  время запроса.

Тест: `tasks/__tests__/AssignedToButtons.test.jsx` (+2: пользователь и группа по
одному Id).

### 13.2 Фильтр «Я исполнитель» = задачи, которые я ВЕДУ

Раньше (§12.4) кнопка сверяла «Кому назначено» (`AssignedToId`), поэтому
показывала и задачи, которые на меня только назначены (никто не взял), и задачи,
которые взял кто-то другой.

Теперь строка проходит фильтр, только если **оба** условия выполнены:

1. задача `В процессе выполнения`/`В работе` **или** завершена
   (`isInProgressStatus` / `isCompletedStatus`); «Не начата» не проходит — у неё
   исполнителя ещё нет;
2. её взял/закрыл текущий пользователь — по тем же признакам, что и карточка
   (`lib/currentUserMatch.isTaskTakenByCurrentUser`): Id взявшего **на сайте
   источника** (`EditorId`, у разных сайтов Id разные), ФИО (`EditorTitle` —
   «Поршаков Сергей» = «Сергей Поршаков Александрович»), учётная запись.

`TasksGrid` для этого получил проп `currentUserTitle` (из `TasksView`), а кнопка
разблокируется, если известен либо Id, либо ФИО. Подсказка:
«Показывать только задачи, которые у меня в работе или завершены мной».

Тест: `tasks/__tests__/TasksGrid.filters.test.jsx` (9, переписан под новую
семантику: своя в работе, своя завершённая, назначенная на меня но не начатая,
в работе у другого, свой Id на сайте ДОБ, совпадение по ФИО).

### 13.3 Заливка строк по статусу задачи

| Статус | Класс строки | Цвет |
|---|---|---|
| Не начата (в срок) | — | без заливки |
| В процессе выполнения / В работе | `tasks-row-progress` | `#fff3e0` бледно-оранжевый |
| Завершена | `tasks-row-completed` | `#e8f5e9` бледно-зелёный |

* просрочка проверяется ДО «в работе»: взятую, но не закрытую в срок задачу

* CSS — только `background-color` (`.ag-row` позиционируется абсолютно, любая

* попутно из `index.css` убрана лишняя закрывающая скобка в конце файла

## 14. Время решения в таблице, кнопка «Исполнитель», зебра и read-only завершённой задачи (2026-10-10)

Пять замечаний пользователя по таблице `#tasks` и по форме завершённой задачи
`#dob_tasks`.

### 14.1 У завершённой задачи в «Сроке» — время решения

Карточка завершённой задачи вместо чипа срока рисует время решения
(`formatSolveTime`: `Решено за 3д 4ч`), а таблица продолжала показывать
`Просрочено 2д 5ч назад` — срок закрытой задачи уже ничего не значит, зато
красный текст пугал. Теперь `dueCellText` ветвится по статусу:

* задача открыта → `formatDueLeft` (`Осталось …` / `Просрочено … назад`), как в §13.4;
* задача завершена → `formatSolveTime` (`Решено за 3д 4ч`, а без дат — просто `Решено`);
* цвет у завершённой — нейтральный `#455a64` (это факт, а не предупреждение).
  Прежнее правило «просрочка закрытой задачи — `#616161`» из §13.4 больше не
  применяется: ячейка закрытой задачи вообще не про срок;
* подсказка (`dueCellTooltip`) у завершённой — `Создана: … • Завершена: … (3д 4ч)`,
  у открытой — точная дата и время срока.

### 14.2 Зебры в таблице нет

### 14.3 «Исполнитель» — кнопка принципала, как «Кому назначено»

Раньше кнопкой был только «Кому назначено», а исполнитель показывался текстом
(а в пяти ветках карточки рядом с подписью «Исполнитель:» вообще стояла кнопка
«Кому назначено»). Теперь обе подписи — кнопки одного вида:

* `AssignedToButtons.jsx` разбит на общий `PrincipalButtons` (иконка
  человек/группа, уточнение типа по Id, клик — карточка принципала) и две
  обёртки: `AssignedToButtons` (AssignedTo) и `TakerButtons` (Editor — тот, кто
  ВЗЯЛ задачу в работу);
* `parseEditors(task)` в `lib/assignees.js` возвращает исполнителя списком
  принципалов и пусто, пока задачу не взяли (Editor SharePoint проставляет и при
  создании — показывать автора как исполнителя нельзя, то же правило, что в
  `resolveTaker`). Id берётся `takerPrincipalIdOf` ТОЛЬКО из Editor-полей:
  `takerIdOf` из `currentUserMatch.js` годится для «моя ли задача», но там есть
  фолбэк на `AuthorId`, и в показе исполнитель превратился бы в автора;
* в таблице колонка «Исполнитель» получила `colId: "taker"` и рендерится
  `TakerCell`; клик по кнопке не открывает поповер действий строки —
  `fromAssigneeButton` смотрит общий признак `[data-principal-button]`;
* в карточке все шесть веток нижней строки рисуют
  `Исполнитель: <кнопка> • Кому назначено: <кнопка> • Статус: …`
  (плюс `ExternalTaskCard` и `TaskElementDialog`).

### 14.4 Завершённая задача `#dob_tasks` блокировалась не полностью

Форма результата открывалась с `readOnly`, но в `ContentTypeResultDialog` общий
набор пропов полей был `const common = { size, fullWidth, disabled: submitting }`
— без `readOnly`. Его переопределяли точечно (richtext, человек, автокомплиты,
чекбокс), поэтому редактируемыми оставались `select`, `multichoice`-список,
`number`, `date`, `multiline` и обычный текст — 7 контролов в диалоге. Правка:
`disabled: submitting || readOnly` в общем объекте, а не в каждой ветке.

Сам `RichEditor` утечкой не был: CKEditor получает `disabled={readOnly}`.

Регрессионные тесты считают редактируемые контролы и требуют, чтобы их не было:
`tasks/__tests__/ContentTypeResultDialog.test.jsx` (+3, всего 16) и
`dob/__tests__/DobTaskEditView.readOnly.test.jsx` (+1, всего 4). Проверено, что
тест не «пустой»: с откаченной правкой он падает и перечисляет 4 редактируемых
контрола на уровне страницы.

### 14.5 Дубликат `variant` в `TaskCard`

Сборка ругалась четыре раза: `Duplicate "variant" attribute in JSX element` —
у четырёх кнопок `variant` задавался дважды, и побеждало последнее значение
(то есть настройка из `TaskBehaviour` молча перекрывалась жёстко прописанным
выше по списку `variant="contained"`). Удалены жёсткие значения; вариант кнопки
теперь всегда из Behaviour с фолбэком (`getActionVariant(...) || "contained"`).
`react/jsx-no-duplicate-props` по всему `src` — 0.

Тесты раунда: `TakerButtons.test.jsx` (4), `assignees.taker.test.js` (6),
`TasksGrid.columns.test.js` (17). `npx vitest run` — 77 файлов / 653 теста,
`npm run build` — без предупреждений, `preview/table-check.mjs` — «Итог: ОК»
