# ADR: форма создания заявки ДОБ по типу контента (обязательные поля)

**Статус:** Accepted
**Дата:** 2026-10-13
**Связанный код:** `src/features/dob/components/requestForm/*`, `src/features/dob/lib/requestFormFields.js`
**Развивает:** `docs/decisions/dob-requests-route-and-create-form.md` (роут `#dob_requests/new` и первые компоненты формы)

---

## Контекст

Роут `#dob_requests/new` уже существовал: форма строилась по выбранному типу
контента списка `Requests`. Пользователь уточнил требования к «стартовой форме
оформления заявки»:

* типов контента будет **до 7**;
* **rich-текст с картинками** — как в задачах (картинки — вложения элемента);
* полей **«Результирующий выбор»** в заявках **нет** — это стартовая форма;
* в форме показываем **только обязательные поля** типа контента;
* **`Title` не показываем** — генерируем общим правилом;
* **`Status` не отправляем** — значение проставит дефолт колонки;
* обязательное поле **lookup быть не может**;
* **картинки — двухфазная запись** (подтверждено);
* тип выбирается **кнопками/чипами на одной странице** (не выпадающим списком).

## Решение

### 1. Тип заявки — чипы на одной странице

`RequestTypePicker.jsx` заменил `RequestContentTypeSelect.jsx` (выпадающий список
удалён): ряд `Chip` из типов контента списка. Подпись — **описание типа**
(`contentTypeDisplayName` → `Description`), внутреннее имя (`Name`) не показываем.
Системная «Папка» (`0x0120…`) из выбора исключена. Тип по умолчанию — первый
подходящий, форма открывается уже с полями.

### 2. Только обязательные поля

`useRequestForm` строит состав формы так:

```
controls = buildRequestFormControls(fields).filter(c => c.required === true)
```

Обязательность берётся из метаданных SharePoint: уровень списка (`Required`) с
перекрытием по `FieldLinks` типа контента (`fetchContentTypeFieldsDetailed`).
Порядок полей — как в типе.

### 2a. Подписи и подсказки — из `Description`

Подпись поля в форме — **всегда `Description`** поля типа контента (в SharePoint
в нём формулируют «что указать в поле»); `InternalName` не показываем никогда.
Функция `requestFieldLabel(field)` — единая точка: `Description` → `Title` (тоже
человекочитаемое) → известный русский оверрайд. Тот же текст идёт и **placeholder**
пустого поля (у текстовых/даты/числа/выбора, у рич-редактора и у поля человека —
для этого в `PersonFieldAutocomplete` добавлен параметр `placeholder`). У rich-поля
название выводится подписью над редактором.

### 3. `Title`, `Status` и «Результирующий выбор» в форму не попадают

Добавлены в `REQUEST_FORM_SKIP_FIELDS` (`requestFormFields.js`): `Title`,
`Status`, `TaskStatus`. Плюс отдельный предикат `isOutcomeChoiceField`
(`OutcomeChoice` / `TypeDisplayName` «Результирующий выбор») — даже обязательное
такое поле не нарисует группу кнопок результата.

### 4. Заголовок заявки — общее правило

`requestTitle.js` → `buildRequestTitle({ contentType, ctLabel, date })`:
`«<Название типа> от <дд.мм.гггг чч:мм>»`. Название типа — из `Description`
(то же значение, что в чипах). Правило одно на все типы; `Title` уходит в payload
при создании. Если позже понадобятся разные шаблоны по типам — добавим override,
не меняя базовое правило.

### 5. `Status` не отправляем

Поле не показываем и не включаем в payload — значение проставит дефолт колонки
(список заявок показывает только `Status = "Открыт"`, см. `DobTasksView`).

### 6. Rich-картинки — двухфазная запись

Вложения/картинки CKEditor привязаны к `id` элемента, которого до создания нет.
`useRequestForm.submit`:

```
Фаза 1 — POST createDobItem:
  • ContentTypeId выбранного типа, обязательные не-rich поля, Title (правило §4);
  • rich-поля: inline-картинки (base64) ВЫРЕЗАЕМ, оставляем текст. Если текста
    нет — непустой плейсхолдер («<p>&nbsp;</p>»), иначе SP отклонит обязательное
    поле. Base64 в SharePoint не уходит.
        │  → id
Фаза 2 (только если есть картинки) — MERGE updateDobItem:
  • materializeRichValues(values, { upload: f => uploadDobAttachment(id, f) }) —
    каждая base64-картинка становится вложением, в тексте остаётся ссылка;
  • rich-поля со ссылками пишем обратно.
```

Переиспользован отлаженный механизм формы правки (`materializeRichValues`,
`uploadDobAttachment`, `attachmentUrl`, `richUploadAdapter`) — картинки становятся
вложениями элемента, ровно «как в задачах». Валидация обязательного rich-поля
учитывает картинку как содержимое (общий `validateRequiredFields` снимает теги и
счёл бы поле с одной картинкой пустым — для проверки подставляется маркер).

Если фаза 2 падает после успешного создания: элемент **не удаляем**, показываем
«Заявка #N создана, но изображения не загрузились» — заявку можно открыть и
дозаполнить (компенсирующее удаление не делаем).

### 7. Гейт рассылки DcEmail (Office + Department)

При создании заявки форма проверяет, есть ли в списке `DcEmail` элемент с
`OffDepKey = Office + Department` (оба — из профиля пользователя, слитно, как в
`tasks/distribution`). **Список `DcEmail` для заявок ДОБ лежит на САЙТЕ ДОБ
(`sites/dob/doblogistic`), рядом со списком `Requests`**, поэтому все запросы идут
через `dobAxios`/`dobApiBase` (свой digest сайта ДОБ), а не через клиент основного
сайта. `resolveDistributionViaDcEmail` получил параметры `get`/`listBase`, чтобы
тот же резолвер можно было направить на нужный сайт (для задач — основной сайт по
умолчанию, для формы заявок — сайт ДОБ). Если элемента **нет** — до создания
заявки пользователь указывает рассылку:

* диалог `DcEmailLinkDialog` + автокомплит **`PersonFieldAutocomplete`** (тот же
  компонент, что и поле «Виновный» в форме задач) — выбор **только групп**;
  поиск идёт по принципалам сайта ДОБ (`/web/siteusers`, как «Виновный»), а НЕ по
  списку `sitegroups`, с **обязательным фильтром `PrincipalType ne 1`** (SP.PrincipalType:
  1 — пользователь, 2/4/8 — группы). Id берутся с того же сайта, что резолвит
  `ensureuser`, поэтому валидны для поля `Email`;
* выбранные группы резолвятся в Id принципала. Порядок:
  0) Id из автокомплита (поиск идёт по `/web/siteusers` — те же принципалы, что
  вернул бы `ensureuser`) — если он подтверждается группой (`sitegroups/getbyid`),
  берём сразу, без лишнего вызова (на AD/security-группах `ensureuser` даёт 404);
  1) иначе `ensureuser` — метод ВЕБА: **`POST /web/ensureuser`** (не
  `/web/siteusers/ensureuser` — это другой ресурс и даёт 404), имя параметра
  пробуем как `logonName`, так и `loginName`; 2) иначе группа по названию
  (`sitegroups/getbyname` → фильтр `Title eq`). В `Email` пользователь не
  попадёт: результат всегда проверяется на группу;
* `ensureDcEmailLink`: если элемент уже появился — используем его; иначе
  **сначала создаём элемент в `DcEmail`** (`OffDepKey` + `Email` =
  `Collection(Edm.Int32)` выбранных групп), и **только затем** создаём заявку в
  `Requests` (порядок обеспечивает `useRequestForm.saveDcEmailAndCreate`).

Если `Office`/`Department` профиля не заданы («Не указано»/пусто) — гейт не
применяем, заявка создаётся как раньше. Ошибку создания элемента `DcEmail`
показываем в диалоге; заявку при этом **не** создаём.

### 8. Резолв группы рассылки и запись в поле `Email`

Два дефекта, из-за которых сохранение рассылки падало (лог из браузера:
`sitegroups/getbyid(6773)` → 500, `siteusers/ensureuser` → 404,
«Обнаружены несовместимые типы. Тип "Collection(Edm.Int32)" относится к виду
"Collection" вместо ожидаемого "Primitive"»):

* **Группу проверяем через `siteusers`, а не `sitegroups`.** Коллекция
  `sitegroups` знает только группы SharePoint (`PrincipalType 8`); группы
  безопасности AD (4) и списки рассылки (2) в неё не входят, `getbyid` на них
  отвечает 500 «Невозможно найти группу». `isGroupPrincipal(id)` теперь читает
  `PrincipalType` из `/web/siteusers/getbyid(id)` и считает группой всё, что не
  пользователь (`!== 1`). Типу из выдачи поиска доверяем — `searchDobGroups` и
  так фильтрует `PrincipalType ne 1`, поэтому для выбранной в автокомплите
  группы резолв идёт без единого запроса.
* **По названию ищем без учёта регистра.** `ensureuser` принимает только точную
  учётную запись, а `sitegroups/getbyname` и `$filter=Title eq '…'` соблюдают
  регистр — «_рц 8117 отгрузка» не находило «_РЦ 8117 Отгрузка». Теперь
  название сверяется со списком групп сайта в нижнем регистре (и по `Title`, и
  по `LoginName`), регистрозависимый фильтр `Title eq` убран, а `ensureuser`
  перенесён в конец цепочки. `searchSiteUsers` для групп дополнительно
  домешивает локальную регистронезависимую сверку.
* **`/web/siteusers/ensureuser` не существует** — `ensureuser` это метод Web
  (`/_api/web/ensureuser`); лишний эндпоинт убран.
* **В поле `Email` пишем тот тип, который ждёт список.** Коллекцию
  `Collection(Edm.Int32)` SharePoint принимает только для поля с
  `AllowMultipleValues`; в одиночное поле (и в число) нужен просто Id. Перед
  записью читаем `/fields` списка DcEmail (`InternalName`, `FieldTypeKind`,
  `AllowMultipleValues`), поле рассылки определяем по имени `Email*`, иначе —
  единственное поле `FieldTypeKind 20`. Если сервер всё же отвечает ошибкой про
  Collection/Primitive — повторяем POST вторым вариантом.

## Что не делаем (по требованиям)

* Lookup в форме создания не поддерживаем — обязательным он быть не может.
* Отдельный блок вложений (не-картинки) в создании не добавляем (есть в правке).
* Поля результата, мастер-визард, создание в диалоге — не нужны.
