# Картинки rich-текста — вложением; детекция задачи ДОБ — по настройке TaskBehaviour

Дата: 2026-10-04 (раунды 9–12).

## 1. Изображения rich-текста сохраняются ссылкой на вложение

**Проблема.** При сохранении заявки/задачи картинка из rich-поля (ChekResult,
DescriptionCheckResult, …) уходила в SharePoint как `data:image/…;base64,…`
(адаптер загрузки CKEditor возвращал base64). Заявка раздувалась на сотни килобайт,
а в карточке/форме картинка была «внутри текста», а не вложением.

**Решение.**
- `RichEditor` загружает картинку вложением элемента
  (`<list>/items(<id>)/AttachmentFiles/add`) и подставляет в текст ССЫЛКУ
  (`src/features/dob/components/richUploadAdapter.js`).
- В SharePoint хранится серверный путь `/sites/…/Lists/…/Attachments/<id>/<file>`,
  а в браузере картинка показывается рабочим адресом: dev — через прокси
  `/dob-api` (NTLM), prod — абсолютным origin. За это отвечает
  `src/features/dob/lib/attachmentUrl.js` (`attachmentStorageUrl` /
  `attachmentDisplayUrl`, `toStorageImages` / `toDisplayImages`).
- Перед сохранением любой оставшийся base64 (старое значение, не удавшаяся
  загрузка) превращается в вложения: `src/features/dob/lib/materializeRichImages.js`
  (`materializeRichHtml` / `materializeRichValues`). Ошибка загрузки не теряет
  текст — картинка остаётся base64, пользователю показывается предупреждение.
- Вложения, которые исчезли из текста, удаляются (сравнение `src` идёт в
  «серверном» виде, иначе `/sites/…` и `/dob-api/sites/…` — одна и та же картинка —
  считались бы разными и вложение удалялось ошибочно).
- **Base64 не сохраняется никогда (раунд 11).** Если картинку не удалось загрузить
  вложением (нет прав, сеть), сохранение останавливается: `fieldsWithBase64`
  (`materializeRichImages.js`) находит `data:image/…` в подготовленных значениях, и
  форма показывает «Изображение не удалось сохранить вложением: <поле>…» —
  в SharePoint уходит только ссылка. Текст в редакторе не теряется: повторное
  сохранение (или удаление картинки) снимает блокировку. Это касается и формы заявки
  (`DobTaskEditView`), и формы задачи типа контента (`TasksView.handleCtDialogSubmit` —
  диалог не закрывается, задача не завершается).
- **Загрузчик прокинут во ВСЕ rich-поля (раунд 11).** И основной rich-текст, и
  rich-поля в «Остальных полях» (форма заявки и `ContentTypeResultDialog`) получают
  `onUploadImage`/`onDeleteImage`, поэтому base64 не появляется ни в одном из них.

Вложений может быть сколько угодно; имена уникализируются (`image_<ts>_<rand>`).

### 1.1 Каскад: текст ↔ вложения (раунд 12)

- **Удалили картинку из текста → удаляется вложение.** `RichEditor` держит
  предыдущий html (`lastHtmlRef`) и на каждое изменение отдаёт наружу исчезнувшие
  картинки (`onDeleteImage`), сравнивая в серверном виде (`/dob-api/…` → `/sites/…`).
  Внешнее обновление значения (загрузка с сервера, сохранение, шаблон) картинок не
  «удаляет»: ref обновляется ДО `setData`. base64/blob — не вложения, они
  игнорируются (`deleteAttachmentForSrc`).
- **Удалили вложение из блока вложений → картинка уходит из текста.** Удаление
  чистит ВСЕ rich-поля формы (`stripAttachmentFromValues` + `removeImgByFileName`,
  сравнение по имени файла, поэтому `/sites/…` и `/dob-api/sites/…` — один файл) и
  rich-текст формы задачи (CT) — через «пульт» `valuesControlRef` у
  `ContentTypeResultDialog` (значения живут внутри диалога, снаружи их можно
  изменить только так). Итог: `#dob_tasks/<id>` и попап `#tasks` ведут себя
  одинаково в обе стороны.

### 1.2 Картинка в редакторе не «битая» (раунд 12)

Причина. Прямая ссылка на вложение (`/sites/<site>/Lists/<list>/Attachments/<id>/<file>`)
идёт через dev-прокси, а NTLM-прокси (`proxy-server.cjs`) качал такие URL как JSON
(`Accept: application/json`): браузер получал испорченный файл, и в rich-тексте
картинка выглядела «сломанной» (в логе — `test load FAIL`).

Решение (две независимые меры):
1. **Адрес показа — REST-запрос содержимого файла** (`attachmentDisplayUrl`):
   `…/_api/web/getfilebyserverrelativeurl('<серверный путь>')/$value` — в dev через
   префикс `/dob-api`, в prod с origin страницы. Сайт берётся из самого пути (всё,
   что до `/Lists/…`), поэтому ссылки обоих списков (основной и сайт ДОБ)
   раскрываются верно. `…/$value` качается бинарём в ЛЮБОМ окружении (Vite-прокси,
   NTLM-прокси), поэтому правка работает и без перезапуска прокси.
   `attachmentStorageUrl` умеет разбирать такой адрес обратно в серверный путь —
   в SharePoint по-прежнему уходит ТОЛЬКО `/sites/…` (несколько преобразований
   подряд идемпотентны).
2. **Прокси различает файлы и `_api`-запросы**: `isBinaryRequest`
   (`scripts/spProxyUrl.cjs`, покрыт тестом) считает бинарём `…/$value`,
   `…/OpenBinaryStream` и ЛЮБОЙ путь вне `_api` с расширением файла. Так прямая
   ссылка тоже работает (запас прочности, например для уже сохранённых значений),
   но для этого нужен перезапуск прокси.

Прокси-префикс один и тот же для обоих сайтов — `/dob-api`: он единственный
проксирует на ORIGIN SharePoint, поэтому `/dob-api/sites/obrazceo/…` (основной
список) и `/dob-api/sites/dob/doblogistic/…` (сайт ДОБ) раскрываются в прямые
ссылки корректно. Правка требует перезапуска прокси (`npm run proxy`).

### 1.3 Значения формы задачи (CT) и React (раунд 12)

`ContentTypeResultDialog` вызывал `onValuesChange` внутри updater'а
`setValues(...)` — React выполняет updater во время рендера, поэтому обновление
родителя (`DobTaskEditView`) попадало в фазу рендера и появлялся варнинг
«Cannot update a component (DobTaskEditView) while rendering a different component
(ContentTypeResultDialog)» (воспроизводился при вставке картинок из буфера).
Теперь значения считаются из ref и наружу сообщаются ПОСЛЕ `setValues`, а
одинаковые словари (`sameFormValues`) не вызывают ререндер — иначе возможен цикл
«форма сообщила → страница перерисовалась → форма сообщила снова».

## 2. Детекция «нашей» формы — по настройке TaskBehaviour (IsDobTask)

**Как НЕ надо (отменено).** Колонка `IsDobTask` в списке задач не подходит: значение по
умолчанию колонки в SharePoint одно на весь список, поэтому «Да» для одного типа контента
проставляется всем задачам списка — признак «расползается» по всем типам сразу.

**Решение.** Признак живёт в `TaskBehaviour` — **по одной записи на тип контента**
(`Title` = `ContentType.Name`), колонка записи `IsDobTask` (Boolean). Фронт:

- `fetchTaskBehaviour` читает поле `IsDobTask` (если колонки ещё нет — повтор запроса без
  неё, остальная настройка сохраняется);
- резолвер CT.Name → Title (`services/taskBehaviour.js`) отдаёт `isDobTask` вместе с
  правилом; общая запись `*`/`_default` признак НЕ включает (иначе флаг у всех задач);
- `markDobTask(task, config)` проставляет задаче `isDobTask: true`; это делают `#tasks`
  (`TasksView.withDobFlag` — таблица, карточки, открытие формы) и страница
  `#dob_tasks/<id>` (`DobTaskEditView`, там дополнительно работает и для задачи,
  открытой напрямую по ссылке);
- `hasDobTaskFlag` (`contentTypeFields`) читает ТОЛЬКО `task.isDobTask` — сырое поле
  элемента игнорируется; далее, как раньше, задача ведётся формой ДОБ
  (`#dob_tasks/<id>?list=…`), результат закрывается формой по колонкам типа контента;
- признак приоритетнее правила Behaviour `dlg: false`; историческая детекция по CT
  «Результат проверки ООБ» (id/имя) остаётся fallback для списков без записи в
  TaskBehaviour;
- polling hash-режима переносит признаки задачи (`ContentTypeId`, `isDobTask`, `raw`) из
  предыдущего состояния — короткий `HASH_POLL_SELECT` их не запрашивает.

Поле в списке TaskBehaviour создаётся идемпотентно:
`node scripts/grant-task-behaviour-list.cjs` (или вручную: TaskBehaviour → добавить
колонку `IsDobTask`, тип «Да/Нет»).

Диагностика: `?dbg=1` → `[TaskBehaviour] resolved { …, isDobTask: true }`.
