# «Результат проверки ООБ»: закрытие через диалог ДОБ по колонкам

**Дата:** 2026-10-04
**Тип контента:** `Результат проверки ООБ`
(базовый id `0x0108003365C4474CAE8C42BCE396314E88E51F00DDA2B3C73567D14D8127B2CBCC18DC19`,
**фактический id в основном списке `463b634e-…` — он же + дочерний сегмент**:
`0x0108003365C4474CAE8C42BCE396314E88E51F00DDA2B3C73567D14D8127B2CBCC18DC1900EA27BBB7EC9C434BA049A0C60A2EA435`;
родитель — «Задача рабочего процесса» (2013), группа `ProblemsPallet`).

## Решение

Задачи этого типа закрываются **только через диалог** — по аналогии с задачами сайта ДОБ.
Форма диалога строится **строго по типу контента и типам колонок**, а не по списку
хендмейд-полей в коде: набор контролов определяется метаданными SharePoint
(`contenttypes('<ctId>')?$expand=Fields`), обязательность — флагом `Required` колонки.

Ответы на уточняющие вопросы (опрос 2026-10-04):

| Вопрос | Решение |
|---|---|
| Состав полей диалога | только предметные колонки: `DobSearchResult`, `DescriptionCheckResult`, `ErrorTypeValidation`, `ErrorCountValidation`, `Guilty`; служебные (`Title`, `StartDate`, `TaskDueDate`, `AssignedTo`, `PercentComplete`, `Body`, `Predecessors`, `Priority`, `TaskStatus`, `RelatedItems`) не показываются |
| Кнопки результата `DobSearchResult` | значения из `Choices` **колонки типа контента** (плюс свежие choices строки таблицы, они тоже читаются из колонки) |
| Как включается диалог | **автоматически по типу контента** — запись в TaskBehaviour не нужна; для произвольного правила остаётся ключ `dlg: true` (синонимы `dialog`, `requiresDialog`) |
| Обязательные поля | ровно те, у которых в SharePoint стоит `Required` (`DescriptionCheckResult`, `DobSearchResult`) |

## Как это работает

| Колонка | Контрол |
|---|---|
| `DobSearchResult` (Результирующий выбор, Required) | кнопки результирующего выбора в диалоге |
| `DescriptionCheckResult` (Многострочный, Required) | rich-текст (обязательное поле результата заявки) |
| `ErrorTypeValidation` (Выбор, `FillInChoice`) | автокомплит с подстановкой своего значения |
| `ErrorCountValidation` (Число) | числовое поле «Кол-во ошибок» |
| `Guilty` (Пользователь или группа) | поиск по **учётной записи** с приведением разделителей `_` → `.`, autocomplete с многократным поиском и выбором; в чипе — имя и должность |

Поля «Пользователь или группа» (`User`/`UserMulti`) собираются общим контролом
`PersonFieldAutocomplete`: запрос к `/web/siteusers?$filter=substringof(...)` по логину
(варианты `ivanov.ii`, `ivanov_ii`, `i:0#.f|membership|...`), отображение — «Имя — Должность»
(должность из `SPS-JobTitle`), значение payload — `Collection(Edm.Int32)` в `<Field>Id`.

Маппинг «колонка → контрол» живёт в `src/tasks/contentTypeFields.js`
(`controlKindOf`/`buildContentTypeForm`/`validateRequiredFields`), сам диалог —
`src/features/tasks/components/ContentTypeResultDialog.jsx`, кэш полей — 30 минут
(`sessionStorage sp:ctFields:<ctId>`).

## Паритет таблицы и карточки

- И карточка, и попап строки таблицы при `dlg` открывают один и тот же диалог;
- `loc` в Behaviour имеет приоритет над `p`/`aa` **и в поповере** — раньше при
  `{ loc: true, aa: true }` карточка показывала диалог «Где найдена ЕО?», а таблица
  инлайн-форму с доп. действиями. Теперь таблица тоже открывает диалог (`buildResultEditor`
  возвращает `null` при `requiresLocation`);
- при `p: [Location1]` без `loc` (настройка пользователя) форма по-прежнему показывается
  прямо в поповере, без диалога местоположения.

## Открытие задачи: как задача сайта ДОБ (2026-10-04, уточнение)

Задача этого типа **не открывается стандартной карточкой `#tasks/<Id>`** — она ведёт себя
как задача сайта `dob/doblogistic`:

| Действие | Поведение |
|---|---|
| Карточка в `#tasks` | read-only карточка ДОБ (`ExternalTaskCard`): «Взять в работу» + «Изменить», без кнопок результата |
| Попап строки таблицы | то же (паритет карточки и таблицы): «Взять в работу» / «Изменить» |
| «Изменить» и deep-link `#tasks/<Id>` | переход на **форму ДОБ** `#dob_tasks/<Id>?list=<GUID основного списка>` (`DobTaskEditView`); «Назад» — в `#tasks` |
| Экран формы | та же форма, но вместо полей заявки — форма закрытия по колонкам типа контента (кнопки `DobSearchResult`, рич-текст, автокомплиты, число, «Пользователь или группа»); «Сохранить» пишет MERGE (`Status=Завершена`, `PercentComplete=1`, поля CT) в основной список |
| «Взять в работу» | основной путь (`handleTakeInWork`): `Status` в основном списке, «Исполнитель» = взявший |

Технически: `openTaskForm`/`buildTaskFormHash` для main-задачи этого типа возвращают
`#dob_tasks/<Id>?list=<TASKS_LIST_GUID>`; `dobApi` научился работать с основным списком
(`listApiOf`/`httpOf`: для `TASKS_LIST_GUID` — основной клиент, для остальных — DOB),
поэтому форма ДОБ читает и пишет элементы основного сайта. `ContentTypeResultDialog`
получил режим `inline` (та же форма без модального окна) — его показывает форма ДОБ.

**Почему таблица всё равно уходила в `#tasks/<Id>` (найдено и починено 2026-10-04).**
Две причины, обе закрыты:

1. `useHashElement` в hash-режиме отдаёт задачу из `useTasksQuery`, к которой `markMainTasks`
   не применяется → `sourceId` пустой; guard в redirect-эффекте `TasksView.jsx` требовал
   строго `sourceId === "main"` и молча выходил, поэтому deep-link `#tasks/<Id>` (именно его
   ставит «Изменить» в таблице, когда строка пришла без типа контента) показывал карточку.
   Теперь «нет `sourceId`» = основной список, guard не блокирует. Проверка: кейс в
   `TasksView.multisource.test.jsx` («#tasks/13 … уводит на форму ДОБ»).
2. Тип контента распознавался только как строка (`contentTypeId`/`ContentTypeId`/`raw.StringValue`).
   Если SharePoint отдаёт его объектом (`{ StringValue }` / `{ Id: … }`), с OData-префиксом
   (`OData__ContentTypeId`) или задачу можно опознать лишь по имени типа, детект молчал.
   Теперь есть `contentTypeIdOf`/`taskContentTypeId`/`taskContentTypeName`/`isResultCheckTask`,
   а `isDialogRequired(rule, ctId, ctName)` принимает и имя типа. Роут `?dbg=1` печатает
   `[DBG:ct-detect]` со всеми формами id — этим и проверяется живой ответ SharePoint.

3. **Главная причина.** `ContentTypeId` у элемента в списке — ДОЧЕРНИЙ тип: к базовому id
   добавлен сегмент `00EA27BBB7EC9C434BA049A0C60A2EA435`. Сравнение «строка == строка»
   с базовым id не совпадало никогда, поэтому задача считалась обычной и открывалась
   карточкой. Теперь id сопоставляется **по префиксу** (`contentTypeIdMatches`,
   однонаправленно: фактический id начинается с известного), известны оба id
   (`RESULT_CHECK_OOO_CT_ID` и `RESULT_CHECK_OOO_CT_FULL_ID` = `RESULT_CHECK_OOO_CT_IDS`),
   плюс работает распознавание по имени типа. Тем же правилом живут конфигурационные
   списки (`taskPromptFields`/`taskResultDefinitions`/`taskTypeConfiguration` — `CType.startsWith`),
   так что поведение единообразное.

4. **Страховка на случай, когда типа контента нет вовсе** (таблица собирает `$select`
   из доступных полей источника — `ContentTypeId` мог не попасть в строку). При открытии
   формы тип дочитывается у самого элемента: `fetchTaskContentTypeId(Id)` →
   `items(<Id>)?$select=ContentTypeId` (кэш на сессию). Это работает и для таблицы,
   и для карточки, и для deep-link `#tasks/<Id>`. Если и там типа нет — остаётся
   прежний маршрут `#tasks/<Id>`.

Диагностика на живом тенанте: `?dbg=1` → в консоли `[DBG:ct-detect]`
(`ct`, `ctName`, `rawCt`, `dobLike`) при открытии меню строки, и
`[DBG:ct-detect] тип контента дочитан у элемента` при дочитывании.

## Что НЕ делаем

- никаких самодельных диалогов/маршрутов «закрыть задачу»;
- не дублируем обязательность полей в TaskBehaviour — источник истины SharePoint;
- не показываем в таблице поля результата (они принадлежат диалогу).

## Состав формы — только FieldLinks типа контента (2026-10-04, round 4)

**Симптом.** В форме `#dob_tasks/<Id>?list=<GUID>` появлялись колонки, которых в типе
контента нет: `AdditionalActions` (MultiChoice) и `AdditionalActionsRequired` (Boolean) —
приложение их не использует, в форме они не нужны.

**Причина.** Состав формы собирался по полям ВСЕГО списка (`/fields`), а это надмножество
типа контента: в списке живут колонки, не добавленные ни в один CT (в т.ч. инфраструктура
«Дополнительных действий»). Фильтрация по имени — не решение (поле с таким именем может
законно быть в CT).

**Решение.** Источник состава — `FieldLinks` типа контента:
`GET <listApi>/contenttypes?$select=Id,StringId,Name&$expand=FieldLinks&$top=50` →
тип ищется по `StringId` (матч по префиксу, как у элементов), берутся `FieldLinks.results`.
Тип/`Choices`/`Required` колонок добираются из `/fields` по `Id`/`InternalName`
(FieldLinks их не отдаёт). Фолбэки: `contenttypes('<id>')?$expand=Fields`, затем все поля
списка (если CT недоступен) — чтобы форма не осталась пустой.
Код: `fetchContentTypeFieldLinks` / `fetchContentTypeFields` (`src/tasks/contentTypeFields.js`),
форма ДОБ — `getDobContentTypeFields(ctId, listGuid)` (`src/features/dob/api/dobApi.js`)
и фильтр `editableFields` в `DobTaskEditView.jsx`.
Проверка: тест «состав формы — только FieldLinks типа контента» — из `/fields` приходят
`AdditionalActions`/`AdditionalActionsRequired`, в форму не попадают.

## Поля формы — по типам колонок (2026-10-04, round 4)

- **Поля выбора — настоящие select.** `choice` без `FillInChoice` → `select` (`controlKindOf`
  отдаёт `select`), `MultiChoice` без `FillInChoice` → `select multiple`; с `FillInChoice`
  остаётся автокомплит со свободным вводом (как требовалось для `ErrorTypeValidation`).
  В форме ДОБ то же правило: любой выбор — `TextField select` (одиночный/многократный),
  включая случай, когда тип не пришёл, но в метаданных есть `Choices`.
- **«Пользователь или группа» — имя, должность, департамент.** `PersonFieldAutocomplete`
  (поиск по учётной записи, `_`→`.`) показывает в подсказке и в выбранном
  «ФИО — Должность · Департамент»: `getUserPosition` тянет `SPS-JobTitle` и
  `SPS-Department` из профиля. В форме ДОБ user-поля больше не read-only текст, а тот же
  автокомплит (многократный — для `UserMulti`), payload: `<Field>Id` и
  `Collection(Edm.Int32)` для многократных.
- **MultiChoice в payload** уходит строкой с разделителем `;#` (как хранит SharePoint).

## «Задача уже взята другим пользователем» — не для исполнителя (2026-10-04, round 4)

**Симптом.** «Заявка на поиск ООБ … В работе у Поршаков Сергей» + «Задача уже взята другим
пользователем. Возьмите другую задачу.» — при том что пользователь и есть Поршаков Сергей.

**Причина.** «Своя/чужая» определялась сравнением `EditorId`/`EditorTitle` с текущим
пользователем: Id на разных сайтах не совпадают (dob ≠ main), `Editor` приходит то строкой,
то объектом, а ФИО сравнивались посимвольно («Поршаков Сергей» ≠ «Сергей Поршаков
Александрович»). У карточек внешних задач вообще передавался только Id сайта-источника,
который мог не срезолвиться.

**Решение.** Общий помощник `isTaskTakenByCurrentUser` (`src/features/tasks/lib/currentUserMatch.js`):
Id взявшего сверяется с Id текущего пользователя НА САЙТЕ ИСТОЧНИКА (для main — Id основного
сайта), ФИО — по словам (порядок и отчество не важны, ё→е), плюс учётная запись
(локальная часть логина). Используется в `TaskCard`, `ExternalTaskCard`, `TaskList`,
`isRowTakenByOther` (`TasksView`) и в мутациях взятия (`useTaskMutations`,
`handleTakeExternalTask`) — при «взял я» показывается «В работе у вас» без предупреждения,
вместо «Возьмите другую задачу».

## Значения выбора и профиль человека: два «странных» места (2026-10-04, round 5)

**1) «Тип ошибки» показывал `[object Object]` вместо пустоты.**
SharePoint (`odata=verbose`) отдаёт MultiChoice объектом-коллекцией
(`{ __metadata: { type: "Collection(Edm.String)" }, results: [] }`, элементы — `{ Value }`),
а в форме значение приводилось к строке (`String(raw)`) — отсюда `[object Object]`.
Добавлены `normalizeChoiceValues` / `normalizeChoiceValue` (`src/tasks/contentTypeFields.js`):
понимают коллекцию, массив, `{ Value }`, строку «a;#b» и пустое значение; используются при
инициализации формы, в рендере (select/autocomplete/multichoice) и в payload
(MultiChoice уходит строкой «a;#b»). То же — в форме ДОБ (`DobTaskEditView`).

**2) Должность/департамент: запросы обрывались на `#` в учётной записи.**
URL вида
`GetUserProfilePropertyFor(...)?@v='i:0#.f|membership|ivanov.ii@lenta.com'`
обрывался на `#` (начало fragment) — SharePoint получал `@v='i:0` и отвечал
«Строка запроса "accountName" отсутствует или недопустима». Плюс на каждого человека
уходило ДВА запроса (JobTitle + Department), то есть до 40 запросов на один поиск.
Теперь:
* `accountNameParam()` кодирует учётную запись целиком (`encodeURIComponent`): `#` → `%23`,
  `|` → `%7C`, `@` → `%40`;
* сначала ОДИН пакетный запрос `/web/SiteUserInfoList/items?$select=Id,UserName,JobTitle,Department&$filter=Id eq … or …` —
  должность и департамент сразу на всех найденных (`fetchPositionsFromUserInfo`);
* для тех, кого в списке сведений нет, — профиль одним запросом
  `GetPropertiesFor(accountName=@v)` (JobTitle + Department), не больше 8 человек за раз;
* если пакетный запрос недоступен (нет полей/прав) — больше не пробуем (флаг на сессию);
* результат по-прежнему кэшируется по логину (повторный поиск в сеть не идёт).
Подпись человека: «Иванов Иван — Главный специалист · Департамент ИТ».

## Единый формат страниц, button group и свойства человека (2026-10-04, round 6)

**1) Страницы форм приведены к одному формату.** Общие стили вынесены в
`src/features/dob/lib/formStyles.js` (`FORM_PAGE_SX`, `FORM_APPBAR_SX`,
`FORM_SECTION_TITLE_SX`, `FORM_FIELD_GRID_SX`, `FORM_FIELD_FULL_SX`,
`FORM_PRIMARY_BUTTON_SX`, `FORM_SECONDARY_BUTTON_SX`, `FORM_ACTIONS_SX`) и используются
и заявкой ДОБ, и задачей «Результат проверки ООБ»: одна шапка с «Обновить»/«Сохранить»,
заголовки секций («Результат проверки», «Остальные поля»), сетка полей 1/3/4 колонки,
компактные поля 32 px со скруглением 4 px, кнопки внизу с тем же градиентом.
Inline-форма задачи больше не «диалог в рамке»: это страница
(`ContentTypeResultDialog` при `inline` рисует секции + строку действий).
`submitRef` позволяет кнопке «Сохранить» в шапке страницы отправлять форму задачи —
как в форме заявки ДОБ.

**2) Результирующий выбор — группа кнопок.** Кнопки результата (DobSearchResult и любой
«Результирующий выбор») теперь `ToggleButtonGroup` (`role="group"`, выбранная — залита
фирменным синим), а не отдельные произвольно оформленные кнопки.

**3) «Пользователь или группа»: офис и раскрытие свойств.** Добавлено поле **Office**:
пакетный запрос — `SiteUserInfoList/items?$select=Id,UserName,JobTitle,Department,Office`
(если в тенанте нет колонки Office — повтор без неё), профиль — `SPS-JobTitle` +
`SPS-Department` + `Office`/`SPS-Office`/`SPS-Location`. Подпись человека:
«Иванов Иван — Главный специалист · Департамент ИТ · СПб, Ленинский 1».
Клик по выбранному чипу раскрывает свойства (Popover): Должность, Департамент, Офис,
Учётная запись; повторный клик закрывает. Кэш сведений — по логину (JSON в sessionStorage,
ключ `sp:userOrg:v3:`), повторный поиск в сеть не ходит.

## Название/описание задачи, кнопки результата и чип человека (2026-10-04, round 7)

**1) Почему не было кнопок результирующего выбора.** Колонка `DobSearchResult`
в живом тенанте имеет тип **`OutcomeChoice`**, а `controlKindOf` такого типа не знал:
`isFormField` возвращал `false`, поле выпадало и из состава формы, и из блока
результата → `choices.length === 0` → блока кнопок не было вовсе («Кнопок
результирующего выбора я не наблюдаю!»). Теперь `OutcomeChoice`/`Combobox`
обрабатываются как выбор, `isResultChoiceField` распознаёт их по `TypeAsString`,
а `buildContentTypeForm` умеет **запасной блок результата** (`fallbackResultField`)
из метаданных СПИСКА задачи — на случай, когда колонки результата нет в `FieldLinks`
типа контента (она заведена на уровне списка). Значения `Choices` нормализуются из
verbose-объектов (`{Value}`), чтобы кнопки не подписывались «[object Object]».

**2) Порядок страницы.** Название задачи — в шапке рядом с номером
(«Задача #712 · <Название>»), описание задачи — сразу в теле (`Body` с снятыми
rich-тегами, абзацы сохранены), затем результат проверки (кнопки), затем основное
поле «Описание результата проверки» (rich-текст) и только потом «Остальные поля».
Раньше «Остальные поля» стояли первыми и в них же попадал rich-текст.

**3) Чип человека.** Чип содержит только имя (должность/департамент/офис — в карточке
по клику, `title` подсказывает полную подпись), поле «Пользователь или группа»
занимает широкую ячейку сетки, а чипы переносятся внутри поля — ничего не выезжает
за края формы.

**4) Инпуты.** Однострочные поля — `min-height: 40px`, подпись и значение — 13px/1.35
(подпись перестала «съезжать» внутри поля); многострочные и множественные поля
растут по содержимому. Единые правила — в `src/features/dob/lib/formStyles.js`,
дизайн-система форм описана в `docs/decisions/form-ui-ux.md`.
